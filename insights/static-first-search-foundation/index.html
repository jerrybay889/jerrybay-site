인사이트 / 구축 방법

정적 사이트에 검색 기반을 만드는 최소 구현 순서

검색 기반은 CMS나 자동 발행부터 시작하지 않아도 됩니다. 공개 URL과 문서의 의미를 먼저 고정하고, crawler가 발견할 파일과 내부 링크를 연결한 뒤, 같은 계약을 자동 검증하면 작은 정적 사이트도 충분히 관리 가능한 Search Foundation을 가질 수 있습니다.

배제협2026.08.12 · 업데이트 2026.08.13약 8분

Answer First — CMS보다 먼저 고정할 5가지

  • 각 공개 문서의 고유 URL, title, description, canonical을 맞춥니다.
  • robots, sitemap, feed가 실제 공개 URL과 같은 truth를 보게 합니다.
  • Home → Hub → Detail → Related/CTA가 crawlable internal link로 연결됩니다.
  • Article/CollectionPage 같은 structured data는 화면의 실제 사실과 일치할 때만 사용합니다.
  • 이 계약을 사람이 기억하지 않아도 되도록 deterministic QA로 고정합니다.

왜 CMS가 검색 기반의 시작점은 아닌가

CMS는 콘텐츠를 편하게 작성하고 관리하는 도구입니다. 그러나 검색엔진이나 AI answer engine이 이해하는 것은 최종적으로 공개된 URL, 문서 제목, 본문 구조, 링크, 이미지와 출처입니다. CMS가 있어도 canonical이 중복되거나 sitemap이 실제 route와 다르면 기반은 약합니다. 반대로 정적 HTML이라도 이 정보가 일관되고 검증되면 검색 가능한 문서 구조를 만들 수 있습니다.

JERRYBAY B2 Search Foundation은 이 순서를 택했습니다. 먼저 정확히 세 개의 공개 가능한 seed article을 만들고, `/insights/`, robots, sitemap, feed, 내부 링크와 QA를 묶어 작은 콘텐츠 시스템을 증명했습니다. 그 뒤에야 운영 규모가 커질 때 Admin CMS를 별도 운영층으로 추가하는 방향을 잡고 있습니다.

1. 문서의 고유한 의미와 canonical URL을 고정합니다.

검색 기반에서 가장 먼저 필요한 것은 “이 문서가 무엇인가”에 대한 일관된 답입니다. 각 상세 페이지는 고유한 title과 description, canonical URL을 가져야 합니다. 공유 화면에 쓰이는 Open Graph title/description/url도 같은 문서를 설명해야 합니다.

글이라면 화면에 보이는 제목, 작성자, 발행일과 `Article` structured data가 일치해야 합니다. 프로젝트 상세라면 실제 내용을 Article처럼 꾸미기보다 `WebPage`나 적절한 공개 구조를 사용하는 편이 낫습니다. Schema는 검색을 속이는 추가 문구가 아니라 문서의 구조를 기계가 이해하기 쉽게 표현하는 계약입니다.

2. robots, sitemap, feed를 같은 URL 목록에 맞춥니다.

robots.txt는 crawler에게 접근 정책과 sitemap 위치를 알려줍니다. sitemap.xml은 canonical public route를 나열합니다. RSS feed는 최신 authority 콘텐츠의 제목, 설명, 발행일과 영구 링크를 제공합니다. 이 세 파일이 서로 다른 URL을 말하거나 삭제된 route를 계속 포함하면 발견성보다 혼선을 만듭니다.

DocumentTitle · Description · Canonical · H1을 정합화.
DiscoverRobots · Sitemap · Feed에 실제 URL을 연결.
ConnectHub · Detail · Related · CTA 내부링크 구성.
VerifyHTML · JSON-LD · links · mobile을 자동 검사.

3. SEO와 GEO가 함께 읽을 수 있는 본문 구조를 만듭니다.

검색 키워드를 반복하는 것보다 중요한 것은 독자가 묻는 질문에 바로 답하고, 그 답의 근거와 세부 설명을 구조화하는 것입니다. JERRYBAY Content OS는 상세 글의 상단에 Answer First를 두고 H2/H3로 문제·원인·방법·사례·체크리스트·FAQ를 구분합니다. 제품명, 회사명, 기술명 같은 Entity는 정확한 이름으로 쓰고, 공개 근거는 Sources/Evidence 섹션에서 분리합니다.

이 방식은 전통적 SEO뿐 아니라 생성형 검색과 AI 답변 환경에서 문서의 핵심 주장과 근거를 파악하기 쉽게 만드는 데도 유리합니다. 다만 GEO를 이유로 새로운 사실을 만들거나 FAQ를 억지로 늘리는 것은 금지해야 합니다.

4. 이미지도 crawlable Evidence로 다룹니다.

상세 글에 들어가는 이미지는 장식보다 이해를 돕는 역할이어야 합니다. 실제 screenshot, prototype, sample, process diagram을 우선하고, 각 이미지에 구체적인 alt text와 caption/source를 붙입니다. AI로 생성한 Concept visual이라면 실제 고객 화면이나 성과처럼 오해되지 않게 `Concept / Illustration / Prototype`으로 표시해야 합니다.

5. 사람이 기억하지 않아도 되는 규칙은 테스트합니다.

정적 사이트는 구조가 단순한 대신 사람이 파일을 직접 수정할 때 drift가 생기기 쉽습니다. 따라서 route 존재 여부, 중복 title, canonical과 OG URL의 일치, sitemap/feed XML, 깨진 내부 링크, JSON-LD parsing을 deterministic check로 고정하는 편이 좋습니다. Browser QA에서는 desktop/mobile 렌더, overflow, menu, console error, 주요 link target을 확인합니다.

Static QA

HTML, canonical, links, sitemap/feed처럼 같은 입력에서 같은 결과가 나오는 검증은 자동화에 적합합니다.

Human / Visual QA

긴 글의 읽기 흐름, 이미지 의미, 모바일 인지부하와 Evidence의 오해 가능성은 별도 리뷰가 필요합니다.

언제 Admin CMS를 추가해야 하나

작성할 페이지가 늘어나고 title, image, source, tag, related content를 사람이 여러 HTML에 반복 입력하기 시작하면 CMS의 가치가 커집니다. 그러나 이때도 Public Site까지 즉시 동적 CMS로 바꿀 필요는 없습니다. JERRYBAY는 별도 Admin에서 콘텐츠를 관리하고 reviewed static export를 GitHub Draft PR로 보내는 구조를 기획하고 있습니다. 이렇게 하면 작성 편의와 정적 공개 구조의 단순성을 함께 가져갈 수 있습니다.

구현 체크리스트

  • 모든 public route에 unique title/description/canonical이 있다.
  • H1은 페이지당 하나이며 본문 H2/H3 hierarchy가 자연스럽다.
  • robots/sitemap/feed URL이 실제 public route와 일치한다.
  • Hub에서 Detail, Detail에서 Related/Business로 crawlable link가 있다.
  • Article schema의 제목·작성자·날짜가 visible copy와 일치한다.
  • 이미지에 descriptive alt와 caption/source가 있다.
  • 중요 콘텐츠에 Sources/Evidence가 있다.
  • 자동 검증과 desktop/mobile browser QA가 release 전에 실행된다.

FAQ

정적 사이트도 SEO에 불리하지 않나요?

정적이라는 이유만으로 불리한 것은 아닙니다. 중요한 것은 crawler가 접근 가능한 고유 URL, 의미 있는 콘텐츠, metadata, 내부링크, 성능과 구조의 일관성입니다.

해시태그를 많이 넣으면 검색에 더 잘 걸리나요?

해시태그는 내부 Topic taxonomy와 탐색에는 유용하지만, 무관한 키워드 반복은 검색 품질을 높이는 핵심 수단이 아닙니다. 본문 의미, 근거, Entity, 내부링크와 metadata가 우선입니다.

자동 발행까지 바로 연결하는 게 효율적이지 않나요?

콘텐츠의 Evidence·Privacy·Visual QA가 안정되기 전에는 Draft PR과 Preview까지 자동화하고 Publish/Merge는 별도 gate로 남기는 편이 안전합니다.
